CHECK-10 -- THE RED TRANSCRIPT
===========================================

CHECK-10 is a property of the RUNNER rather than a module under tools/checks/,
and that is exactly why this file exists. The reasoning is the same as its
sibling for CHECK-11 and is set out there in full: an earlier plan's audit derives its
population from a check-module glob and a transcript glob, a runner property
matches neither, and without these two files "every checker has already FAILED on
a real defect" would read as satisfied over nine of eleven.

WHAT CHECK-10 REQUIRES, verbatim from the project requirements document:

    A check may be waived only by a waivers[] entry carrying
    {check_id, reason, dated_at}, and the checker prints the waiver count in its
    summary, so waivers are countable rather than invisible.

Two halves. The SHAPE, and the COUNT. Both are stubbed below, and both fail on a
verdict.

THE CONTROL a design rule (HARD) ADDS ON TOP OF THE SHAPE
--------------------------------------------------
A waiver present in a run's output that was not in the LAST COMMITTED version of
waivers.json is ITSELF a finding. The reason is not fastidiousness: build agents
run unattended, and a waiver a build agent can write is not a waiver, it is an
off switch on the checker that agent is being measured by. The owner round trip
-- a human, a reason, and a commit -- IS the feature.

So the runner reads the working copy, reads the committed copy back through git,
and compares them. Reading the committed copy from git rather than from a cache
the same process wrote is the whole mechanism; a cached comparison would be the
run agreeing with itself.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
tools/conformance.py was REGISTERED AND RUNNABLE when this was captured. It
discovered the check package, ran every module that exists at this wave, printed
a population line for each, built both runner rows, aggregated the codes and
wrote the structured report. Two named stub points carried the CHECK-10 property,
and nothing else:

    resolve_waivers()          the run's own waivers record is honoured as
                               written; the committed copy is NEVER consulted, so
                               a waiver the owner did not commit silences the
                               finding it names
    waived_count_for_line()    the waiver count printed beside every check is
                               hard-wired to zero, whatever the run actually read

Every failure line below is therefore an assertion about a VERDICT produced by a
runner that really ran, over inputs that really exist.

READ THE QUOTED CHECK-10 LINE IN THE SECOND FAILURE. The run honoured one waiver
-- the line says `honoured=1` in its own note -- and printed `waived=0` on the
same line. That pair, in one line, is CHECK-10's second half failing in the most
legible way it can: the count is present, and it is wrong. A wrong number reads
as detail where a missing one would have read as a question. The last failure in
this run shows the same disagreement at `honoured=2`.

THE FIXTURE, AND WHY ITS DEFECT IS NOT IN THE COMMITTED BYTES
--------------------------------------------------------------
fixtures/broken-artifacts/broken-uncommitted-waiver/ is the committed one-known-
bad input. What it commits is the SHAPE -- a valid, owner-authored waiver
and the record that holds it -- because the defect itself cannot be committed:

    a waiver that is UNCOMMITTED stops being uncommitted the moment it enters
    the index.

The tests therefore copy that tree, commit the copy through
conftest.committed_tree, and write a SECOND waiver into the working copy only.
The committed half is the baseline the checker compares against; the added half
is the defect. That is stated in the fixture's own README rather than left for a
reader to work out from the absence.

REVIEW CRITERION FOR THIS FILE, stated so it can be checked rather than assumed:
the failure lines below must name ASSERTIONS ON THE VERDICT. A transcript whose
failure line instead names a failed module load, a collection failure, an absent
input, or an argument parser rejecting a flag is a FALSE RED and must be rejected
and recaptured. That is mechanically checkable with a case-insensitive grep over
five shapes, and the plan states the pattern.

THE PATTERN IS DELIBERATELY NOT PASTED HERE, for the reason its sibling file sets
out: a transcript that quoted its own needle set would match that grep against
its own prose and fail the gate it exists to satisfy. It returned 0 against this
file when this was captured, and against the raw pytest output before it was
framed.
