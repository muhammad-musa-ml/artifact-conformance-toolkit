CHECK-02 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-02 REQUIRES, verbatim from the project requirements document:

    Fails when the README date is absent, or does not equal the date component
    of a machine-emitted `started_at` in a results file.

WHY THIS CHECK HAD NOTHING TO COMPARE AGAINST UNTIL AN EARLIER PLAN
----------------------------------------------------------------
The date is the single easiest field in an artifact to TYPE rather than derive,
and a typed date looks exactly like a derived one. The shared pattern note probed both
shipped artifacts for started_at / finished_at / dated_at / isoformat and found
exactly ONE hit, and that hit is a synthetic log document's field rather than a
run stamp. So until the run-metadata emitter existed, this check had no machine
side at all and could only ever have reported that a date looked like a date.

That is why this module REFUSES rather than passes when it finds no machine
stamp. "There was nothing to compare against" is not "the date agrees", and the
distinction between those two is the one a design rule calls the most important in the
checker.

THE ASSERTION THIS WHOLE SUITE IS BUILT AROUND
------------------------------------------------
a design rule stores timestamps BOTH ways: `started_at` local with a real offset, and
`started_at_utc` beside it. They can name DIFFERENT DAYS, and on this machine
they routinely do. MEASURED while this check was written, one instant read two
ways:

    started_at       2026-09-15T19:57:50-05:00      the fifteenth
    started_at_utc   2026-09-16T00:57:50+00:00      the sixteenth

For roughly five hours of every day the two disagree about the date here. So
WHICH FIELD THE CHECK READS IS THE CHECK. A version comparing against the UTC
stamp would pass the tree this suite expects it to refuse and refuse the tree it
expects it to pass, while every population number it printed stayed identical.
test_the_comparison_is_against_the_local_date_not_the_utc_one asserts both
directions, and the committed fixture is built on exactly that straddle.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap in that requirement is that "before
the implementation" reads as "before any code exists", and a transcript captured
then records a module that could not be loaded or an input that was never
written. Each of those exits non-zero, each satisfies a naive "non-zero exit"
acceptance test, and none of them says anything about whether the check
DISCRIMINATES.

So tools/checks/check_02.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it, it walked results/, it excluded the gate record and the
per-item records and counted both exclusions, it parsed every machine stamp, it
located the artifact:date region, it extracted the rendered date, it counted the
local-versus-UTC divergences, it reported a population and it wrote a structured
report. ONE function was stubbed:

    date_findings()   returns no finding, whatever the two dates say

READ THE QUOTED POPULATION LINES IN THE FAILURES BELOW. The first says

    CHECK-02  PASS  found=0 checked=1 of 2 skipped=1 floor=1 waived=0
    readme-date=2026-01-01 machine-dates=1 (2026-09-15) results-files=1 of 2
    utc-date-differs=1

The check READ the rendered date. It READ the machine date. It even counted that
the UTC counterpart falls on a different day. The two dates it printed side by
side are nine months apart. And it printed PASS. That is precisely the shape a
false RED cannot demonstrate: the inputs were real, the measurement happened,
and only the verdict was wrong.

THE FIXTURE, AND WHY IT IS A COMPLETE ARTIFACT RATHER THAN A STUB
--------------------------------------------------------------------------
fixtures/broken-artifacts/broken-readme-date-mismatch/ renders the day AFTER the
day its machine recorded. Its run began at half past ten at night, local, on the
fifteenth; the UTC counterpart of that same instant falls on the sixteenth. The
README renders the sixteenth. The date was read off the wrong one of two fields
that are both present, both well formed and both genuinely machine-written.

A date typed at random would be caught by any comparison at all. This one is
caught ONLY by a check that knows which of the two stored stamps it compares
against -- a check reading `started_at_utc` reports this tree CLEAN.

Everything else about the tree is correct on purpose: a passing gate whose
dated_at precedes every measurement, a complete run record carrying both
timestamp forms and all three cost fields, and a figures record whose figure
carries its denominator. test_only_check_02_refuses_the_check_02_fixture runs
CHECK-01 and CHECK-03 over it and asserts both PASS, so "the checker refused it"
says WHICH checker did the refusing. That test passes in the run below.

ONE TEST IN THIS SUITE WAS WRONG AND WAS REPAIRED BEFORE THIS CAPTURE, and the
repair is recorded here rather than quietly made. The zero-input test originally
asserted that the banned verdict word does not appear anywhere in stdout. It
does appear -- canonkit.report prints `skipped=N` as a legitimate COUNT LABEL on
the same line, and the banned word is banned as a VERDICT. A substring test over
the whole line cannot tell a count label from a verdict, so it failed on a
CORRECT refusal. That is the same shape as the guards an earlier plan had to withdraw:
a check that matches its own vocabulary rather than the thing it is about. The
assertion now reads the verdict COLUMN, and it passes in the run below, which is
what makes its pass evidence rather than noise.

REVIEW CRITERION FOR THIS FILE, stated so it can be checked rather than assumed:
the failure lines below must name ASSERTIONS ON THE VERDICT. A transcript whose
failure line instead names a failed module load, a collection failure, an absent
input, or an argument parser rejecting a flag is a FALSE RED and must be
rejected and recaptured. That is mechanically checkable with a case-insensitive
grep over five shapes, and the plan states the pattern.

THE PATTERN IS DELIBERATELY NOT PASTED HERE. A transcript that quoted its own
needle set would match that grep against its own prose and fail the gate it
exists to satisfy -- and the natural repair for that, excluding this file from
the sweep, would put a hole exactly where the guard is supposed to be. The
pattern lives in the plan's acceptance criteria. It returned 0 against the raw
pytest output below, and against this assembled file.

The bug: ISO_DATE_RE ended in `\b`, under a comment claiming it found the date
component of a full timestamp. It does not. The character after the day in
2026-09-15T20:08:11-05:00 is `T`, a WORD character, so there is no boundary
there and the match fails. Every test in the capture above passed over that
expression because all of them typed a BARE date into prose -- and render.py
writes a region body as a KEY HOLE, so the one document that actually matters,
the generated artifact's own README, reads

    <!--artifact:key:dated_at-->2026-09-15T20:08:11.856801-05:00<!--/...-->

and the check reported `readme-date=ABSENT` with the date sitting in plain
sight. It was caught by running the walking-skeleton round trip, not by this
suite: eighteen green tests were consistent with a check that could not read the
only form production produces. The verbatim output above is left exactly as
captured; only this forward-looking paragraph is corrected.
