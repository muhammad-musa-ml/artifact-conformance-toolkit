CHECK-04 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-04 REQUIRES, verbatim from the project requirements document:

    Fails when `results/gate.json` is absent, when its `dated_at` is not earlier
    than every measurement's `started_at`, or when a measurement lacks the gate
    token. A correctly recorded FAILED gate is a PASS for this check.

THE BRANCH THAT MUST NOT FIRE
-------------------------------
The last sentence of the requirement is the part a check written to "refuse
anything that looks wrong" gets backwards. A gate that FAILED, wrote a full
record, named what failed, minted its token and had that token stamped on the
run is a correctly closed path -- not a defect. All three facts CHECK-04 asks
about hold. Refusing it would collapse "this path did not measure, and said so"
into "this path measured without authorisation", and only one of those is a
finding.

a design rule is what makes this checkable at all: a failed gate mints a token
PRECISELY so a measurement that ran anyway carries a key rather than no key.

ORDERING IS PROVEN FROM THE RECORDS, NEVER FROM THE FILESYSTEM
----------------------------------------------------------------
The convenient answer -- compare the two files' modification times -- is wrong
here for reasons that are measured rather than stylistic. An ordinary copy
PRESERVES that attribute, so a results tree carried forward from an earlier
session arrives with entirely plausible times on every file; and it is a single
command to set. templates/verify.py records the same argument for the same
reason.

So the ordering is read from the ISO timestamps recorded INSIDE each record.
Two tests assert that rather than trusting it: one sets a MISLEADING file time
-- the measurement stamped an hour before the gate, while the recorded stamps
stay correct -- and asserts the verdict does not move; the other tokenizes the
check module and asserts no CODE token names that attribute, which catches the
`st_` and `get` spellings by the same assertion.

READ THE SECOND OF THOSE TWO CAREFULLY IN THIS RUN. The misleading-file-time
test PASSES below, and that pass is NOT evidence: a check whose detection is
stubbed to find nothing ignores the filesystem the same way it ignores
everything else. It becomes evidence in the GREEN commit, where the check has
something to say and still says nothing about the file times. It is listed among
the passes below with that caveat attached rather than counted as a win.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap is that "before the implementation"
reads as "before any code exists", and a transcript captured then records a
module that could not be loaded or an input that was never written. Each exits
non-zero, each satisfies a naive "non-zero exit" acceptance test, and none of
them says anything about whether the check DISCRIMINATES.

So tools/checks/check_04.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it, it walked results/, it excluded the gate record and the
per-item records and counted both with a reason beside each, it parsed the
gate's dated_at and every measurement's started_at, it loaded every token, it
reported a population and it wrote a structured report. ONE function was
stubbed:

    gate_findings()   returns no finding, whatever the ordering says

READ THE QUOTED POPULATION LINE IN THE FIRST FAILURE. It says

    CHECK-04  PASS  found=0 checked=1 of 1 skipped=0 floor=1 waived=0
    gate=ABSENT measurements=1 of 1

The check LOOKED FOR THE GATE, RECORDED THAT IT WAS NOT THERE, printed that
fact in its own summary line -- and returned PASS over an artifact in which
nothing authorised anything. That is precisely the shape a false RED cannot
demonstrate: the inputs were real, the measurement happened, and only the
verdict was wrong.

THE FIXTURE, AND WHY IT CARRIES TWO DEFECTS RATHER THAN ONE
--------------------------------------------------------------------
fixtures/broken-artifacts/broken-gate-after-measurement/ carries two defects
belonging to the SAME check, which is a different thing from a fixture that
fails several checks at once:

    the gate is dated an hour AFTER the run that figures.json records
    a second run record carries no gate token at all

Two defects, two finding ids, and a THIRD run record that is correct in both
respects -- so a rule that simply refused every record would fail the fixture's
own test rather than pass it. Everything else about the tree is correct on
purpose, and test_only_check_04_refuses_the_check_04_fixture runs CHECK-01,
CHECK-02 and CHECK-03 over it and asserts all three PASS.

THAT TEST ALREADY EARNED ITS PLACE, BEFORE THE CHECK WAS EVEN WRITTEN. Its
first run failed: CHECK-01 reported four unclassified numerals in the fixture's
own README, because the prose named record and module filenames -- and a
filename carrying a run number is a numeral CHECK-01 cannot classify in
un-rendered prose. The fixture was refused by a check that has nothing to do
with its defect. The README now DESCRIBES those files instead of spelling them,
and says so in the document itself. Without that test the fixture would have
been committed carrying a second, accidental defect, and every later assertion
about which check refused it would have been ambiguous.

WHAT THIS CHECK DOES NOT DO, DEMONSTRATED RATHER THAN CLAIMED
---------------------------------------------------------------
test_check_04_and_verify_answer_different_questions_about_one_token builds the
chain by RUNNING THE REAL GATE, so the token is one the gate genuinely minted
from its own content, and then walks two states. Both were measured in this run:

  state one   the gate FAILED and was correctly recorded, the run carries that
              gate's token. CHECK-04 passes. verify.py ALSO has nothing to say,
              and the captured output below shows `VERIFY-DERIVE PASS`. Neither
              is broken; each is answering its own question truthfully.
  state two   the gate is fixed and re-run. a design rule makes the token a function of
              gate CONTENT, so the new gate mints a DIFFERENT token and the
              measurement is left carrying a key that opens nothing. The
              captured output shows `VERIFY-DERIVE FAIL found=1`. THAT is where
              a design rule's poisoned token becomes visible, and verify.py is what says
              so.

Only the final assertion of that test fails below -- the one about CHECK-04's
own verdict in state two -- because that verdict is the stubbed one.

REVIEW CRITERION FOR THIS FILE, stated so it can be checked rather than assumed:
the failure lines below must name ASSERTIONS ON THE VERDICT. A transcript whose
failure line instead names a failed module load, a collection failure, an absent
input, or an argument parser rejecting a flag is a FALSE RED and must be
rejected and recaptured. That is mechanically checkable with a case-insensitive
grep over five shapes, and the plan states the pattern.

THE PATTERN IS DELIBERATELY NOT PASTED HERE. A transcript that quoted its own
needle set would match that grep against its own prose and fail the gate it
exists to satisfy. The pattern lives in the plan's acceptance criteria. It
returned 0 against the raw pytest output below, and against this assembled file.
