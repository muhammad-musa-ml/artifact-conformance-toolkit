CHECK-08 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-08 REQUIRES, from the project requirements document, PARAPHRASED ON PURPOSE:

    Fails on any unpinned dependency specifier, any image reference lacking
    `@sha256:`, and the floating tag whose name means "newest" ANYWHERE.

The substitution in that last clause is the first thing this check has to
explain about itself, and the rest of this transcript is downstream of it.

THE MEASURED FALSE POSITIVE -- A LITERAL IMPLEMENTATION FLAGS A CORRECT ARTIFACT
---------------------------------------------------------------------------------
The shipped results/provenance.json carries an images mapping whose KEY is
`grafana/k6` plus the floating tag and whose VALUE is `grafana/k6@sha256:e7ee...`.

That record is not a defect. The key is the human-readable name of what was
resolved; the value is the digest it resolved TO. The record is the artifact
DOCUMENTING its own resolution, which is the entire purpose of a provenance
record -- and a check that fails on the string anywhere reports it as a pin
failure.

What makes that worse than an ordinary false positive is the repair it invites.
The finding points at a provenance key, so the obvious fix is to DELETE THE
PROVENANCE KEY: destroy the evidence to silence the checker. The artifact then
passes and is strictly worse than before, and nothing records that this happened.

Two warning signs are therefore stated in the module's own docstring, so a future
reader diagnoses the CHECKER rather than the artifact:

    1. a CHECK-08 finding whose path:line is inside results/ is a SCOPING BUG in
       the checker. results/ is not a pull site and never becomes one.
    2. a "fix" that consists of deleting a provenance key is the failure the
       paragraph exists to prevent.

Both are asserted rather than documented. test_a_correctly_pinned_artifact_with_
a_floating_tag_provenance_key_passes builds exactly that artifact and requires
code 0; test_no_finding_may_ever_point_inside_results parks a compose-shaped file
full of unpinned references inside results/ -- as tempting as the scoping bug
could possibly be -- and requires that nothing is reported from it. Both PASS in
the capture below, and that is correct: they are scope properties, satisfied by a
check whose detection returns nothing, so they were never going to be RED lines.
They are named here because they are the reason this module is shaped the way it
is, and a reader looking for them in the failure list would not find them.

AN EXCLUSION THAT DOES NOT PRINT IS AN EXCLUSION LIST THAT GROWS SILENTLY
---------------------------------------------------------------------------
So both numbers print on every run:

    pull-sites checked N file(s), provenance entries skipped M

M is obtained by READING the provenance records and counting their image entries,
not by ignoring the directory and hoping. The scope line also carries the file
count per category, the driver-scan status, and the number of directories visited
and pruned.

A DEFECT IN THAT REPORTING WAS FOUND AND FIXED DURING THIS CAPTURE, and it was
found by a test failing for the wrong reason rather than by inspection. Rooted at
fixtures/, the check pruned both broken-* trees, found zero pull sites, and
refused -- with a note that said "no pull site of any kind" and said NOTHING about
the two directories it had just declined to walk into. A reader had no way to
distinguish "this tree declares no dependencies" from "I refused to look where
they live". The refusal path is the path that needs the scope counts MOST, which
is the opposite of the intuition that a refusal has nothing to report. scope_note()
now prints them on every path, refusals included.

THE WHOLE FILE IS SCANNED, NOT ONLY THE `image:` KEYS
-------------------------------------------------------
This is not this module's invention. templates/docker-compose.yml states it as
the contract that template was written against, and gives the reason: a
COMMENTED-OUT SERVICE IS ONE UNCOMMENT AWAY FROM BEING A PULL SITE.

The template also records what that cost it: a comment explaining the ban by
QUOTING the banned string is itself a hit -- in every artifact generated from that
template, forever. Its first draft did exactly that and failed this check, and it
now describes the tag in words.

check_08.py is under the same constraint, because it is a .py file inside the
repository it can be pointed at, and IT HIT THE SAME TRAP. The first draft of its
docstring quoted the requirement verbatim, twice, and a grep over the finished
module returned 2. The needle is now ASSEMBLED FROM PARTS at import time -- the
same device check_03.py uses for the skeleton's marker -- and
test_the_module_under_test_carries_no_literal_floating_tag asserts the module
carries none while this test file, which is outside the default scope, carries
several. The difference between the two files is checked rather than remembered.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
tools/checks/check_08.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it. It walked the tree, counted the directories it visited and
pruned, opened every pull site, parsed every specifier and every image reference
into a site carrying its file and its line, read the provenance records, counted
their entries, reported a population and wrote a structured report. ONE function
was stubbed:

    pin_findings()   returns no finding, whatever it is handed

Read the quoted population line in any of the ten failures: the reference counts,
the per-category file counts, the prune counts and the provenance skip count are
all present and all correct, printed beside the word PASS. That is precisely the
shape a false RED cannot demonstrate -- the inputs were real, the parse happened,
the numbers are right, and only the verdict is wrong.

reason an earlier plan recorded: a transcript quoting its own needles would match the

canonkit declares `skipped` a BANNED VERDICT -- it "reads as deliberately and
safely omitted", which is how a zero population gets filed as a pass by a human
reading the log -- and conformance.py owns the `not-examined=` vocabulary in its
place. A check's note is APPENDED TO the runner's population line, so it is
inside that ban, and CHECK-11 fails any run in which the banned word appears
there.

MEASURED: with the banned spelling in place, the full suite reported 11 failures.
Eight of them were integration tests with nothing to do with pins -- they failed
because CHECK-11 went red over one word in CHECK-08's note. The word was changed,
and two tests now guard it: one asserts the printed phrasing, and
test_the_note_never_uses_the_banned_verdict_word asserts the note carries
core.BANNED_VERDICT nowhere, reading the constant rather than restating it.

This is the LIVE-versus-FROZEN distinction applied to a transcript: the captured
output is a historical record and stays verbatim; the framing prose around it
describes current behaviour and has been reconciled. The passing-assertion list
above still names the old phrasing, and that is the one place a reader would
otherwise have been misled.
