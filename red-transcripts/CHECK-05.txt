CHECK-05 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-05 REQUIRES, verbatim from the project requirements document:

    Fails on a missing register row, reported as `expected N, found M`

THE SHORTCUT THAT WORDING INVITES, AND WHY THIS CHECK REFUSES IT
------------------------------------------------------------------
"reported as `expected N, found M`" reads like two numbers to PRINT, and the
shortest way to print two numbers is to read them off the document you are
checking. `tools/build_register.py` writes its own summary line into every
register it generates:

    - expected 12, found 12

A check that lifted those numbers would agree with the register about the
register. It would report a clean run over a document that carries eleven rows
while claiming twelve, and it would do so with both numbers present and both
numbers wrong -- the count-present-but-wrong failure, which reads as detail
where a missing count would have read as a question.

So this check COUNTS THE ROWS. The committed fixture is built to make that the
difference between a pass and a finding: its summary line deliberately claims
the full count while its body carries one row fewer, and
test_the_check_counts_rows_rather_than_believing_the_documents_own_summary is
the assertion. That test is one of the eight below.

A SET COMPARISON, NOT A COUNT COMPARISON
------------------------------------------
The second reason a count is not enough: a register carrying the right NUMBER of
rows with the WRONG SLUG in one of them is a document a reader would be actively
misled by, and a count comparison reports it clean. The comparison here is over
the slug SETS, and `test_an_extra_row_for_an_unexpected_slug_is_a_finding`
constructs exactly that state -- twelve rows, twelve expected, one of them wrong
-- and asserts both halves fire.

THE EXPECTED NUMBER IS READ, NEVER TYPED, AND THAT IS ASSERTED BOTH WAYS
--------------------------------------------------------------------------
`counts.register_rows_expected` is read from tools/manifest.json at run time.
That manifest already holds a committed literal asserted against its own
derivation (the slugs carrying `register_row: true`), so the manifest is the
tripwire. A second copy of the number inside check_05.py would be a third value
that can drift from both, and the drift would be invisible -- a checker agreeing
with itself.

Asserted positively by test_the_expected_count_equals_the_manifests_committed_
literal, which reads the manifest AT TEST TIME so a manifest edit moves both ends
of the assertion together. Asserted negatively by test_the_expected_count_is_not_
typed_into_the_check_source, because a positive assertion alone is satisfied by a
hard-coded constant that happens to agree today. Both were already passing when
this was captured -- they are properties of the module, not of its verdict.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap in that requirement is that "before
the implementation" reads as "before any code exists", and a transcript captured
then records a module that could not be loaded or an input that was not there.
Each of those exits non-zero, each satisfies a naive "non-zero exit" acceptance
test, and none of them says anything about whether the check DISCRIMINATES.

So tools/checks/check_05.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it. It read the manifest, read the committed literal, derived the
expected set, resolved the artifacts root, located the register at that root,
parsed its rows, probed all fourteen slug directories for the `status` rules,
counted the excluded slugs with their reasons and wrote a structured report. ONE
function was stubbed:

    register_findings()   returns no finding, whatever it is handed

READ THE QUOTED POPULATION LINE IN THE FIRST FAILURE. It says

    CHECK-05  PASS  found=0 checked=12 of 14 skipped=2 floor=1 waived=0
    expected 12, found 11 | built 2 of 14, pending 12, rows 11 of 12 |
    excluded: 2 (reasons recorded) | artifacts-root=... slugs-probed=14

The check MEASURED twelve expected rows and ELEVEN found. It printed the
shortfall, in the requirement's own words, on the same line as the verdict. And
it printed PASS. That is precisely the shape a false RED cannot demonstrate: the
inputs were real, the measurement happened, the numbers are right, and only the
verdict is wrong.

A FALSE RED FIRED DURING THIS CAPTURE AND IS RECORDED HERE RATHER THAN QUIETLY
REPAIRED
-------------------------------------------------------------------------------
The first capture of this run held NINE failures, not eight. The ninth was
test_every_file_in_the_fixture_is_tracked, and it failed with

    5 fixture file(s) are present but UNTRACKED

which is a statement about an input that was not there yet, not a verdict. The
fixture had been written to disk but not staged, and `git ls-files` reads the

by implementing anything, which is the definition of a false RED.

The repair was to stage the fixture before re-capturing -- the same repair plan

supposed to be. The pattern lives in the plan's acceptance criteria. It returned
