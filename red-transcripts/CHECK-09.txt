CHECK-09 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-09 REQUIRES, verbatim from the project requirements document:

    Fails when the claim-under-test block is missing: canon + project + bullet
    id, the bullet text verbatim, the measured counterpart, and a verdict in
    {SUPPORTS, SUPPORTS-WITH-REVISION, DOES-NOT-SUPPORT}. A missing verdict
    FAILS. Whether the verdict is CORRECT is human review.

WHY THIS CHECK CARRIES the project overview document's KEY DECISION a design rule
------------------------------------------------------
a design rule reads "a measured number that differs from the canon figure WINS and the
published entry changes". Until a machine can read the claim a measurement is being
weighed against, that sentence is an intention. The claim block -- canon,
project, bullet id, the bullet's text VERBATIM, the measured counterpart and one
of three verdicts -- is the record that makes it enforceable.

(Two different design rules carry that name. The context note's is the dual
timestamp decision. The one above is the project overview document's Key Decision, and it is
qualified everywhere it appears rather than left as a bare id.)

THE TWO DEFECTS THIS CHECK EXISTS FOR, AND WHY A REVIEWER MISSES BOTH
----------------------------------------------------------------------
1. AN AMBIGUOUS ID. 17 of the 49 bullet ids in tools/canon-bullets.json exist in
   BOTH canons -- re-derived at execution time from the snapshot's own
   id_collisions_list, not quoted. A bare `P2-B1` therefore names two different
   bullets in 35% of cases, and a checker that picked one would be wrong a third
   of the time while printing a pass. `P2-B1` is one of the seventeen: it is
   "Traced 58% of p95 latency to retrieval" in example-alpha and "Retired 30
   hand-run steps a week" in example-beta. Those are not near neighbours.

   ROADMAP and the project overview document compound it by calling example-beta's paths BP-1..BP-5
   while the canon stores them as P1..P5. `BP-2-B1` must therefore reach
   example-beta:P2-B1 and must NEVER reach example-alpha:P2-B1. That mapping is
   canon-specific data, so it is resolved through the snapshot's own derived
   `display_ref` values. A pattern that stripped the `B` would send every
   example-beta figure to an alpha bullet in all seventeen colliding cases and
   would look correct on the thirty-two that do not collide.

2. A PARAPHRASE. The bullet text in an artifact is compared to the snapshot on
   ENCODED BYTES, with nothing normalized. No casefold, no whitespace collapse,
   no unicodedata.normalize, no dash or quote folding. Normalization is exactly
   how a paraphrase passes: an NFC and an NFD spelling of the same accented word
   render identically on screen and are different bytes, and so is "a  b" beside
   "a b". Exactly one removal happens first, and it is delimiter removal rather
   than normalization -- the spaces markdown table syntax requires around a
   cell's content.

WHAT THIS CHECK DOES NOT DO
----------------------------
It NEVER judges whether the verdict is RIGHT. Whether a measured figure would
mislead a reader of the bullet is a reading bounded by that bullet's own
metric_basis, and the validation note lists it as manual-only with the
owner as its named human. This check verifies a verdict EXISTS and is one of
three legal strings. A check that claimed to decide the rest would be a check
that cannot discriminate, dressed as rigour.

THE CLAIM TABLE IS FOUND STRUCTURALLY, NOT BY THE ANCHOR
---------------------------------------------------------
Measured from the two skeletons this program ships:
README-SKELETON.md puts the claim-under-test table INSIDE its
`artifact:claim` region. RESULTS-SKELETON.md puts a DIFFERENT table -- the
headline before/after table -- inside its `artifact:claim` region and leaves the
claim-under-test table OUTSIDE it, further down the file. A check keyed on the
anchor reads the wrong table in one of the two. So a claim table is any
contiguous two-column markdown table whose first column carries the claim field
labels; the anchor is recorded beside each table and never keyed on. This is the
same lesson an earlier plan paid for when `startswith("canonkit.")` matched the
FILENAME and produced 26 confident false findings: judge structurally, never by
where a thing happens to sit.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap in that requirement is that "before
the implementation" reads as "before any code exists", and a transcript captured
then records a module that could not be imported or an input that was not there.
Each of those exits non-zero, each satisfies a naive "non-zero exit" acceptance
test, and none of them says anything about whether the check DISCRIMINATES.
an earlier plan's first RED capture was a genuine instance: its anti-rot pin read an
expectation file that did not exist.

So tools/checks/check_09.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it. It loaded the frozen core by path as a sibling, loaded the
canon snapshot with an explicit encoding="utf-8", read README.md, found the
claim table structurally, split its `Bullet id` cell into tokens, enumerated the
figures record, counted a real population, reported it, and wrote a structured
report. ONE function was stubbed:

    claim_findings()    returns no finding, whatever the table says

The two committed expectation files -- fixtures/broken-artifacts/*/
expected-CHECK-09.json -- were written by hand from the specification BEFORE the
detection existed, so the pins below judge the implementation rather than record
it.

READ THE QUOTED POPULATION LINE IN EVERY FAILURE. It says

    CHECK-09  PASS  found=0 checked=2 of 2 skipped=0 floor=1 waived=0
              references=2 tables=1 absent=0 bare-bullet-id=0 unknown-key=0
              text-mismatch=0 no-counterpart=0 verdict=0 documents=1 of 2

checked=2 and tables=1 are the proof that the check LOOKED: it found one claim
table, resolved two bullet references and printed the effective floor. found=0
is the stub. Every failure below is therefore an assertion about a VERDICT.

THE COMMAND
------------
    python -m pytest tools/tests/test_check_09.py -q > .reports/p0112-red09.txt 2>&1
    echo "EXIT=$?"     ->  EXIT=1

Redirected rather than piped, and the exit code read from $? of the REAL command.
A command piped into tail returns the PIPE's status, which is how "EXIT=0" gets
printed beside a failing run.

Interpreter: .venv/Scripts/python.exe, Python 3.12.11, pytest 9.1.1.
