CHECK-06 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-06 REQUIRES, verbatim from the project requirements document:

    Fails when a results file carries no machine-emitted run record.

and a project requirement, which says what such a record IS:

    A run-metadata emitter writes `started_at` and `finished_at` (ISO-8601 with
    offset), the environment fingerprint, and `{api_spend_usd, gpu_minutes,
    wall_seconds}` into every results file -- written by the run, never by a
    human.

AN OMITTED KEY AND A ZERO ARE DIFFERENT CLAIMS
----------------------------------------------------------
A run that spent nothing writes 0.0. It does not omit the key.

The two are indistinguishable to the ordinary defaulting read -- `.get(key, 0.0)`
returns the same thing for both -- so an omitted key travels downstream as a run
that cost nothing. a project requirement re-derives each path's metered spend and GPU hours
from exactly these records BEFORE the owner is asked to approve that path, which
makes this the difference between a number the owner acts on and a number nobody
recorded. The suite tests the pair in one test so the two rules cannot quietly
collapse into one.

A NAIVE TIMESTAMP PRESENTED AS UTC, AND THE HALF A TZINFO TEST CANNOT REACH
------------------------------------------------------------------------------
The failure the research note names is `utcnow().isoformat() + "Z"`: the object was
NAIVE, and the appended letter claims UTC. The obvious rule -- reject a stamp
that parses without tzinfo -- catches only half of it, and this was MEASURED on
this interpreter rather than assumed:

    datetime.fromisoformat("2026-01-01T00:00:00Z").tzinfo is None   ->  False

The hand-assembled string parses as AWARE and sails straight through a tzinfo
check. What catches it is a second measured fact about the same interpreter:

    datetime.now(timezone.utc).isoformat()   ->  '2026-09-16T00:57:50+00:00'
    datetime.now().astimezone().isoformat()  ->  '2026-09-15T19:57:50-05:00'

`datetime.isoformat()` NEVER emits a literal Z. It writes an offset. So a Z
suffix is proof the string was assembled by appending a suffix rather than
produced by a clock, which is the utcnow()-plus-Z shape by construction. Both
arms report the NAIVE case BY NAME, because "invalid timestamp" would send an
author hunting for a typo.

test_a_naive_timestamp_with_an_appended_z_is_rejected_by_name builds the string
from a genuinely naive datetime and ASSERTS THE TZINFO TEST WOULD CLEAR IT
before asserting the check refuses it -- so the test cannot silently degrade
into one that exercises the easy arm.

WHERE A RESULTS FILE'S RUN RECORD LIVES, AND WHY THAT IS THREE PLACES
------------------------------------------------------------------------
Not always inside the file. `results/figures.json` is a DERIVED view: it carries
figures and a gate token and no cost fields of its own, and demanding the seven
fields inside it would make every correctly generated artifact fail. So the
record is located in one of three places, tried in order, and WHICH ONE was used
is printed:

    inline      the file carries a run id, so it IS a run record
    run-block   the file carries a `run` object (the provenance document)
    by-token    a record under results/raw/ carries the same gate token

A file for which none of the three finds a record is carrying numbers that no
machine run stands behind. That is the finding the requirement names.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap is that "before the implementation"
reads as "before any code exists", and a transcript captured then records a
module that could not be loaded or an input that was never written. Each exits
non-zero, each satisfies a naive "non-zero exit" acceptance test, and none of
them says anything about whether the check DISCRIMINATES.

So tools/checks/check_06.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it, it walked results/, it classified every file into the
population or out of it with a reason, it counted both kinds of exclusion, it
indexed the run records under raw/ by their gate token, it LOCATED each results
file's record through the three-place lookup and it printed which location each
came from. ONE function was stubbed:

    record_findings()   returns no finding, whatever the record is missing

READ THE QUOTED POPULATION LINE IN THE UNBACKED-FIGURE FAILURE. It says

    CHECK-06  PASS  found=0 checked=1 of 1 skipped=0 floor=1 waived=0
    records-located=0 of 1 (inline=0 run-block=0 by-token=0)
    results-files=1 of 1

The check tried all three locations. It found the file carried no run id, no run
block, and a gate token that matched nothing. It printed `records-located=0 of 1`
in its own summary line -- and returned PASS over a figure that no run stands
behind. That is precisely the shape a false RED cannot demonstrate: the inputs
were real, the lookup ran, and only the verdict was wrong.

THE FIXTURE, AND WHY BOTH ITS DEFECTS BELONG TO THIS CHECK
-------------------------------------------------------------------
fixtures/broken-artifacts/broken-no-run-record/ carries:

    a provenance record whose run block is complete EXCEPT for the metered-spend

Two defects, two finding ids, two different repairs -- "run the measurement
through the emitter" and "record what the run spent". A single verdict covering
