CHECK-11 -- THE RED TRANSCRIPT
===========================================

CHECK-11 is a property of the RUNNER rather than a module under tools/checks/,
and that is exactly why this file exists.

Every other checker in this phase is a tools/checks/check_NN.py with a matching
red-transcripts/CHECK-NN.txt, and an earlier plan's audit derives its population from
those two globs. A runner property matches NEITHER glob. Without this file and
its sibling for CHECK-10, "every checker has already FAILED on a real defect"
would read as satisfied over nine of eleven -- a verifying population that
excludes precisely the two cases it was written to cover. So the two runner
properties get the same RED-first evidence as the nine modules, captured the
same way, held to the same standard.

Their implementation module is tools/conformance.py, not a check_NN.py. That is
the mapping through which an audit resolves them, and the report's own checks[]
rows carry `"source": "runner:conformance.py"` so the mapping is readable from
the artifact rather than only from this paragraph.

WHAT CHECK-11 REQUIRES, verbatim from the project requirements document:

    The checker prints its own population for every check it runs, and a check
    that ran over zero inputs is reported as FAIL -- never as PASS, and never as
    the banned verdict word.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap in that requirement -- the research note
names it as Pitfall 2 -- is that "before the implementation" reads as "before any
code exists", and a transcript captured then records a module that could not be
loaded or an input that was not there. Each of those exits non-zero, each
satisfies a naive "non-zero exit" acceptance test, and none of them says anything
about whether the check DISCRIMINATES.

So tools/conformance.py was REGISTERED AND RUNNABLE when this was captured. It
discovered the check package, ran every module that exists at this wave, printed
a population line for each, built both runner rows, aggregated the codes and
wrote the structured report. Three named stub points carried the CHECK-11
property, and nothing else was stubbed:

    normalize_zero_population()   a check that examined zero inputs is reported
                                  with code 0 -- the 0/0 pass in its purest form
    scan_over_zero_artifacts()    a scan that enumerated nothing returns 0 and
                                  prints `checked 0 of 0`
    check_11_findings()           the detection returns no finding, whatever the
                                  records say

Every failure line below is therefore an assertion about a VERDICT -- assert
0 == 2, assert 0 == 1, a finding id absent from a list a real detector would
have filled -- produced by a runner that really ran, over inputs that really
exist. The stub's own population line is quoted inside each assertion message,
so a reader can see what the runner concluded and what the test expected, side
by side.

THE LINE WORTH READING TWICE is CHECK-01's in the first failure:

    CHECK-01   DID-NOT-RUN  found=0 checked=0 of 0 ...  (STUB: zero population
    reported as a pass)

The printed VERDICT already says DID-NOT-RUN, because canonkit.report() puts the
zero-population branch first and the runner never re-derived it. What the stub
changed is the CODE beside it, and the artifact-level exit that aggregates from
it. That is the more dangerous shape of this defect, not a milder one: the log a
human reads says one thing while the integer a script branches on says another,
and only the integer travels. It is also why CHECK-11's real detection, landed in
the GREEN commit, reports `verdict-code-mismatch` as a finding of its own.

WHAT THE THREE MEASURED INSTANCES BEHIND THIS CHECK WERE, in this phase alone:
a test command whose own count was suppressed printed dots and no number, so a
verdict carried no population at all; a guard whose vacuity check fired only at
zero ran over two directories instead of twenty-five and PASSED; and a register
whose rows carrying a figures record were zero of twelve correctly exited
DID-NOT-RUN rather than publishing an empty register. A count that is PRESENT but
WRONG is more dangerous than a missing one, because a wrong number reads as
detail while a missing one reads as a question.

REVIEW CRITERION FOR THIS FILE, stated so it can be checked rather than assumed:
the failure lines below must name ASSERTIONS ON THE VERDICT. A transcript whose
failure line instead names a failed module load, a collection failure, an absent
input, or an argument parser rejecting a flag is a FALSE RED and must be rejected
and recaptured. That is mechanically checkable with a case-insensitive grep over
five shapes, and the plan states the pattern.

THE PATTERN IS DELIBERATELY NOT PASTED HERE. A transcript that quoted its own
needle set would match that grep against its own prose and fail the gate it
exists to satisfy -- and the natural repair for that, excluding this file from
the sweep, would put a hole exactly where the guard is supposed to be. an earlier plan
measured what the same mistake costs: a text predicate that matched the FILENAME
it was written to protect produced 26 confident false findings. The pattern lives
in the plan's acceptance criteria and in the research note's Pitfall 2 warning-sign
list. It returned 0 against this file when this was captured, and against the raw
pytest output before it was framed.

its report -- from a working directory with nothing to do with either. What
failed is the verdict, and only the verdict.
