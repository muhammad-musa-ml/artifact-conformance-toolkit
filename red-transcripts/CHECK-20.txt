CHECK-20 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-20 REQUIRES, verbatim from the project requirements document:

    Fails when a slug the manifest marks `built` has left its collections entry
    uncorrected -- every bullet id the manifest maps to that slug must carry
    either a recorded correction or a recorded confirmation, its
    designed-not-yet-measured marker must be gone, and the phase record must
    carry the before/after rows. Exit 2 on a zero population.

WHY THIS CHECKER EXISTS AT ALL, WHICH IS THE THING THE OTHER ELEVEN CANNOT SAY
--------------------------------------------------------------------------------
Every other checker asks whether an artifact is WELL FORMED. This one asks
whether the artifact's existence CHANGED ANYTHING. An example project can be run end
to end, satisfy all eleven other checkers, take its register row and leave the
collections entry exactly as it was -- every light green, and the entire
deliverable skipped. Nothing inside the artifact records what the claim used to
say, so that state is invisible from inside it by construction. This is the
gate that makes it visible.

THE SHORTCUT THE WORDING INVITES, AND WHY THIS CHECK REFUSES IT
------------------------------------------------------------------
"its designed-not-yet-measured marker must be gone" reads like ONE condition,
and a checker built on it alone is about six lines long: scan the row, look for
the marker, report. That checker passes three different broken states.

    a row whose marker was deleted and nothing measured
    a row that is not in the entry at all -- its marker is gone TRIVIALLY,
        because there is nothing to carry one
    a claim the measurement AGREED with, where nobody wrote the agreement down

The third is the one this programme is most likely to hit, and it is the reason
a recorded CONFIRMATION counts. "The measurement agreed" is a RESULT. Inferring
it from a row nobody touched is inferring a measurement from silence, which is
the whole failure mode one directory up.

So the check reads three things, and they are independent on purpose:

    the record       does a correction or confirmation NAME this claim?
    the record       does it say what MOVED -- the before and the after?
    the live entry   is the marker gone, and is the row even there?

test_a_row_still_carrying_its_marker_is_a_finding is the one that proves the
independence: it hands the check a claim that is fully RECORDED and still
marked, and a checker that stopped at the record would call it clean.

THE POPULATION IS THE BUILT SLUGS, AND THE OBLIGATIONS ARE A SECOND NUMBER
----------------------------------------------------------------------------
The requirement's failure condition names a SLUG, so the verdict rests on the
built slugs and ZERO BUILT SLUGS IS THE REFUSAL. Saying "no built path has left
its entry uncorrected" over no built paths at all is a true sentence and it is
not a result.

The OBLIGATIONS those slugs carry are counted separately and printed beside the
first number, never folded into it, because a run that examined two slugs
carrying no claims and a run that examined two slugs' claims are different runs
and only the printed pair can tell them apart. A built slug that maps to no
claim is named in `slugs_without_obligation` rather than dropped.

BOTH MAPPING FIELDS COUNT
---------------------------
The expected set splits the mapping deliberately: `bullets` is what a path is
responsible for backing, `backs_bullets` is what an already-existing artifact is
CITED as backing. A check reading only the first would be blind to exactly the
slug in the committed expected set that is already `built` AND already cited --
a confident zero produced by the scope of the needle rather than by the state of
the world. The union is the obligation set, and
test_a_bullet_reached_only_through_backs_bullets_is_still_an_obligation is the
assertion.

THE MARKER NEEDLE IS READ, NEVER RE-DECLARED
----------------------------------------------
tools/check_canon_backing.py owns the marker and the measured reason its needle
stops where it does: one canon's wording interpolates an example project id, so a
longer and more specific-looking literal matches that canon's rows and none of
the other's -- it halves the population and reports no error. A second copy here
would be a second thing to keep true, so the needle is loaded from that module
by path and this check declares none of its own. Where that module is not
reachable the check REFUSES rather than falling back to a literal nobody
reconciled.

WHAT MAKES THIS A REAL RED RATHER THAN AN ACCIDENT
-----------------------------------------------------
The module is REGISTERED and RUNNABLE in the commit that captures this file. It
imports, it parses its arguments, it prints a population line, it writes a
structured report. Its run() simply returns a PASS over a population of zero --
the exact verdict this programme is organised around making impossible -- and
every failure below is an assertion about a VERDICT.

Three of the sixteen PASS against the stub, and that is not a gap: they assert
the module's own shape (its declared id, its floor, its callable run) and the
fixture's shape (that it carries all three of its own inputs, and that its
records directory holds no fragment). Those are true of the stub and must stay
true of the implementation, so they are green in both commits by design.

Counted needles, so this file cannot quietly become its own false positive: the
five warning signs of a false red occur 0 times each in the framed text, and
