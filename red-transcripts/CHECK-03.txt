CHECK-03 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-03 REQUIRES, verbatim from the project requirements document:

    Fails when the "what this does not show" section is absent, is
    byte-identical to the template placeholder, falls under its word floor, or
    contains no scope vocabulary -- an unedited template copy must not pass.

THE CRITERION THIS REPLACES, AND WHY IT WAS AN UNRUN CHECK
------------------------------------------------------------
The inherited acceptance criterion was a heading count: grep the README for the
limitations heading and require at least one hit. A COMPLETELY UNEDITED TEMPLATE
COPY SATISFIES IT. The heading survives every copy untouched, so the criterion
reports a pass over an artifact in which nobody has written a single word of the
thing being checked. That is not a weak check; it is an unrun one.

The heading is not even stable. The two artifacts that shipped before this
program existed use two DIFFERENT limitations headings -- one calls the section
"what this benchmark is NOT", the other "honest limits on these numbers" -- so a
check keyed on either literal passes one artifact and fails the other. Both are
measured, from the files, not supposed. This check therefore keys on the ANCHOR,
`artifact:limits`, and never on heading text; the region is the addressing
mechanism and the heading above it is free prose.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
a design rule requires the transcript to be captured BEFORE the implementation commit,
with commit order as the evidence. The trap in that requirement is that "before
the implementation" reads as "before any code exists", and a transcript captured
then records a module that could not be loaded or an input that was not there.
Each of those exits non-zero, each satisfies a naive "non-zero exit" acceptance
test, and none of them says anything about whether the check DISCRIMINATES.

So tools/checks/check_03.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it, it read the README, it located the region, it counted the
words, it looked for the scope terms, it hashed the body against the committed
placeholder constant, it cross-checked the LIVE skeleton, it reported a
population and it wrote a structured report. ONE function was stubbed:

    limits_findings()   returns no finding, whatever the body says

READ THE QUOTED POPULATION LINE IN THE FIRST TWO FAILURES. It says

    CHECK-03   PASS   found=0 checked=1 of 1 ... region=ABSENT words=0 of 40
    scope-terms=0 documents=1 of 1 skeleton=checked

and, for the unedited placeholder,

    CHECK-03   PASS   found=0 checked=1 of 1 ... region=present words=22 of 40
    scope-terms=0 documents=1 of 1 skeleton=checked

The check MEASURED that the region was absent. It MEASURED twenty-two words
against a floor of forty. It MEASURED zero scope terms. It even confirmed it
could reach a live skeleton to cross-check against. And it printed PASS. That is
precisely the shape a false RED cannot demonstrate: the inputs were real, the
measurement happened, and only the verdict was wrong.

THE FIXTURE, AND WHY IT IS DELIBERATELY BROKEN IN ONLY ONE WAY
----------------------------------------------------------------------
fixtures/broken-artifacts/broken-unedited-limits/ carries a limits body that is
byte-identical to templates/README-SKELETON.md's own placeholder, hashing to the
constant the plan that authored that skeleton recorded. Everything else about
the tree is CORRECT on purpose: its figures record is well formed and every
figure carries its denominator, so CHECK-01 passes over it. A fixture that failed
several checks at once would make "the checker refused it" unable to say which
check did the refusing, and the fixture would stop discriminating. One of the
passing assertions in this run is exactly that.

The fixture's own heading is deliberately NOT the skeleton's, so a check that
quietly started keying on the heading again would report the tree clean and the
test beside it would go red.

REVIEW CRITERION FOR THIS FILE, stated so it can be checked rather than assumed:
the failure lines below must name ASSERTIONS ON THE VERDICT. A transcript whose
failure line instead names a failed module load, a collection failure, an absent
input, or an argument parser rejecting a flag is a FALSE RED and must be rejected
and recaptured. That is mechanically checkable with a case-insensitive grep over
five shapes, and the plan states the pattern.

ONE OF THOSE FIVE FIRED DURING THIS CAPTURE, and the repair is recorded here
rather than quietly made. The first capture of this run held a genuine false RED:
the anti-rot pin test read an expectation file that did not exist yet, and the
resulting failure named an absent path instead of a verdict. The expectation file
is a committed statement of the INTENDED verdict, so it belongs in the RED commit
and not in the GREEN one -- with it present, the same test fails by comparing a
stubbed verdict against the pinned one, which is the assertion it was written to
make. The capture below is the re-run.

THE PATTERN IS DELIBERATELY NOT PASTED HERE. A transcript that quoted its own
needle set would match that grep against its own prose and fail the gate it
exists to satisfy -- and the natural repair for that, excluding this file from
the sweep, would put a hole exactly where the guard is supposed to be. The
pattern lives in the plan's acceptance criteria. It returned 0 against this file
when this was captured, and against the raw pytest output before it was framed.
