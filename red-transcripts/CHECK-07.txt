CHECK-07 -- THE RED TRANSCRIPT
===========================================

WHAT CHECK-07 REQUIRES, verbatim from the project requirements document:

    Fails when the artifact is not a git work tree, has zero commits, or has no
    tracked machine-written file under `results/` -- verified with
    `git ls-files`, not with "the file exists"

THIS CHECK IS THE TRUE ROOT, AND ZERO OF FOURTEEN SLUGS PASS IT TODAY
-----------------------------------------------------------------------
Measured and recorded in the shared pattern note: `ls -d <artifact>/.git` fails with the
shell's absent-path error for BOTH artifacts that existed before this programme
did. Neither is a repository. Four other checks are unsatisfiable until that is
fixed, and an earlier round owns the fix. This module is not reporting a surprise -- it is
the thing that makes an already-known absence countable.

(That error's exact wording is DESCRIBED rather than quoted here, deliberately.
It is one of the five shapes the false-RED sweep hunts for, and a transcript that
reproduced it in its own prose would trip the gate it exists to satisfy. The
first draft of this file did quote it, and passed the sweep only because the
line-wrap happened to split the phrase across two lines -- grep is line-based.
A gate that passes on an accident of formatting is not a gate, so the quotation
was removed rather than the line-break relied upon.)

THE LITERAL READING OF THE REQUIREMENT IS TOO WEAK, AND THAT IS MEASURED
--------------------------------------------------------------------------
"no tracked machine-written file under results/" is satisfied by ONE such file,
and results/figures.json is always the first to qualify. an earlier plan measured what
that costs, inside a generated artifact after a full run:

    git -C <artifact> check-ignore -v results/raw/run-0001.json
      -> .gitignore:56:raw/      results/raw/run-0001.json

    git ls-files results/  ->  results/RESULTS.md
                               results/figures.json
                               results/gate.json
                               (and ZERO per-item records)

The artifact's own ignore rules swallowed results/raw/, where the per-item run
records live. The rule `raw/` sits in a licence block whose job is keeping SOURCE
CORPORA out of the index, and a bare directory pattern matches at ANY DEPTH, so
two different meanings of the word "raw" collided.

What makes that a known hazard rather than a typo is the direction of the failure. Nothing
went red. The chain this programme exists to prove is

    per-item records -> count(predicate) -> numerator -> / denominator
    -> rendered

and verify.py re-walks it. With the records outside the index, a reader who
clones the artifact holds the CONCLUSION and none of the EVIDENCE, and
`verify.py --tier derive` on that clone re-derives over ZERO items. an earlier round
re-runs every artifact from exactly that clean checkout. And CHECK-07, in its
literal form, PASSED -- because figures.json was tracked. The check was green
while the property it stands for was broken.

So this module asserts the PROPERTY, not the PROXY. An artifact carrying a
TRACKED figures.json must also carry its per-item records in the index. Two
failure modes, two finding ids, because they have two different repairs:
`records-untracked` (they are on disk and git is ignoring them -- and the check
runs `git check-ignore -v` and NAMES THE RULE AND LINE, because that one line is
the whole diagnosis) and `records-absent` (there are none at all).

THE PIN THAT KEEPS THE REPAIR IN PLACE IS IN THE SUITE, NOT IN THIS FILE
--------------------------------------------------------------------------
`test_the_live_template_gitignore_does_not_swallow_the_per_item_records` builds a
throwaway repository carrying templates/.gitignore VERBATIM, writes a per-item
record, a figures record, three source-corpus files and a frozen id list, runs
`git add -A`, and reads the INDEX. It asserts the record went in, the three
corpora stayed out and the id list went in -- both directions, because a negation
that admitted everything would satisfy the admission half and defeat the licence
rule it sits beside.

That test measures the LIVE TEMPLATE'S BEHAVIOUR, not its text, so it fails the
moment the scoped negation is reverted. It PASSES in the capture below, and that
is correct: it is a property of the template, not of this check's verdict, so it
was never going to be one of the RED lines. It is named here so a reader looking
for a known hazard's guard does not go looking in the wrong list.

A DIRECTORY NESTED IN ANOTHER REPOSITORY IS NOT A WORK TREE
-------------------------------------------------------------
`git rev-parse --is-inside-work-tree` answers TRUE for any directory beneath any
repository. The committed fixture must NOT be a work tree while living inside one
that is, so omitting a nested .git is not enough on its own -- a naive branch one
would walk up, find this repository, and report the fixture as a perfectly good
work tree. The module compares `git rev-parse --show-toplevel` against the
artifact directory and treats "inside a work tree whose root is somewhere else"
as NOT a work tree, naming the enclosing toplevel.

It then declines to evaluate the tracked-ness branches at all, and prints
`tracked-ness not-evaluated` with the reason. Those branches would be measuring
the ENCLOSING repository's index -- and the fixture's files genuinely ARE tracked
by artifact-conformance-toolkit, so a check that reported that would print a reassuring
truth about an artifact with no version control whatsoever.

WHAT MAKES THIS A REAL RED RATHER THAN A MISSING FILE
------------------------------------------------------
tools/checks/check_07.py was REGISTERED AND RUNNABLE when this was captured.
Discovery found it. It ran git, resolved the work tree, measured the enclosing
toplevel, counted the commits, listed the index, counted the per-item records on
disk and in the index, read the ignore rule swallowing them out of
`git check-ignore -v`, reported a population and wrote a structured report. ONE
function was stubbed:

    worktree_findings()   returns no finding, whatever it is handed

    CHECK-07  PASS  found=0 checked=5 of 5 skipped=0 floor=1 waived=0
    work-tree=NO commits=0 results-on-disk=5 | tracked-ness not-evaluated (...)
    | enclosing-toplevel=...

The check MEASURED that this is not a work tree. It printed `work-tree=NO`. It
named the enclosing toplevel. It counted five files under results/. And it
printed PASS on the same line. That is precisely the shape a false RED cannot
demonstrate: the inputs were real, the measurement happened, the facts are right,
and only the verdict is wrong.

A FALSE RED FIRED DURING THIS CAPTURE AND IS RECORDED HERE RATHER THAN QUIETLY
REPAIRED -- AND IT IS THE FOURTH INSTANCE OF ONE SHAPE IN THIS PHASE
-------------------------------------------------------------------------------
The first capture held NINE failures. The ninth was
test_the_check_asks_git_rather_than_the_filesystem_about_version_control, and it
failed like this:

    check_07.py asks the filesystem about .git on 1 line(s):
      ["# git, by subprocess. Never os.path.exists('.git')."]

THE GUARD MATCHED ITS OWN PROHIBITION COMMENT. The line whose entire purpose is
to say "never do this" was itself the violation the guard reported. Nothing in
the module does what the guard was hunting for; the guard could not tell a live
call from a sentence describing one.

This is the shape that has now bitten four times in this phase: an earlier plan's hook
check matched `exit 0` in its own comment; an earlier plan's `startswith("canonkit.")`
matched the FILENAME and produced 26 confident false findings; an earlier plan's RED
transcript failed its own gate by pasting the pattern it documented. The repair
here is the one an earlier plan made -- replace the text match with a STRUCTURAL predicate.
`executable_lines()` blanks comments with `tokenize` and docstrings with `ast`,
preserving line numbers, so what the guard scans is code and only code. It trims
a TRAILING comment rather than blanking the line beside it, because a stripper
that blanked whole lines would hide a real violation that happened to carry one;
`test_executable_lines_blanks_a_comment_but_keeps_the_code_beside_it` asserts
exactly that, so the helper the guard rests on is itself checked rather than
trusted.

The needle set that detects a false RED is DELIBERATELY NOT PASTED HERE. A
transcript quoting its own needles would match that sweep against its own prose
and fail the gate it exists to satisfy, and the natural repair -- excluding this
file from the sweep -- would put a hole exactly where the guard belongs. The
pattern lives in the plan's acceptance criteria. It returned 0 against the raw
pytest output below, before that output was framed, and 0 against this file.
